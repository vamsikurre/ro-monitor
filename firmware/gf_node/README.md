# gf_node — ground-floor Wi-Fi nodes

One ESP-IDF project, two roles. Polled by the terrace hub over the LAN
(`docs/superpowers/specs/2026-09-07-ground-floor-wifi-nodes-design.md`).

| Role | Node | Reads |
| :--- | :--- | :--- |
| Sump | `0x05` | AJ-SR04M ultrasonic, or a 4-20 mA transducer when `J-PRESS` is shunted |
| Utility | `0x06` | 3 borewell CTs, 3 sump-motor CT channels, Astero `PUMP ON`, RWT floaty, SHT30 |

## Build

ESP-IDF 5.4.4 shell:

```powershell
. C:\Espressif\tools\Microsoft.v5.4.4.PowerShell_profile.ps1
cd C:\orbit\git_repos\ro-monitor\firmware\gf_node
```

One tree, two roles, and **one thing you must not skip**: ESP-IDF keeps a
single `sdkconfig` at the project root no matter which `-B <dir>` you build
into. `-B` only chooses where the compiled *output* goes — the config file
that decides which role gets compiled still resolves to the same shared path
unless you also pin it with `-D SDKCONFIG=<dir>/sdkconfig`. Build both roles
with `-B build_sump` / `-B build_util` alone and the second `idf.py`
invocation you run — on *either* directory, even a routine rebuild — silently
reconfigures whichever directory it touches to match whatever role was
configured last. Both `.bin` files come out looking fine and are the same
firmware.

That is not hypothetical: it happened while this project was first built,
and it does not show up as a build error. It shows up on the hub, later, as
a node that reports the wrong `id` in `/api/telemetry`, gets rejected
wholesale by the hub's parser, and shows as offline with nothing but
`unparseable reply` in the log — because a sump-role hub config was received
from a utility-labelled binary, or vice versa.

The fix is to pass `-D SDKCONFIG=<build dir>/sdkconfig` on **every**
invocation for both roles, not only on `set-target`:

```powershell
# Sump role (the default Kconfig choice)
idf.py -B build_sump -D SDKCONFIG=build_sump/sdkconfig set-target esp32
idf.py -B build_sump -D SDKCONFIG=build_sump/sdkconfig menuconfig   # SSID, password, static IP
idf.py -B build_sump -D SDKCONFIG=build_sump/sdkconfig build
idf.py -B build_sump -D SDKCONFIG=build_sump/sdkconfig -p COMx flash monitor

# Utility role
idf.py -B build_util -D SDKCONFIG=build_util/sdkconfig -D SDKCONFIG_DEFAULTS="sdkconfig.defaults;sdkconfig.util" set-target esp32
idf.py -B build_util -D SDKCONFIG=build_util/sdkconfig menuconfig   # SSID, password, static IP
idf.py -B build_util -D SDKCONFIG=build_util/sdkconfig build
idf.py -B build_util -D SDKCONFIG=build_util/sdkconfig -p COMx flash monitor
```

`-D SDKCONFIG_DEFAULTS` only matters on `set-target`, since that is the step
that seeds a *new* config file from `sdkconfig.defaults` plus
`sdkconfig.util`. `-D SDKCONFIG=<dir>/sdkconfig` matters on every command,
forever — drop it once and the next invocation falls back to the shared root
file again.

`sdkconfig.util` is **hand-authored and committed**, not generated — it is
the utility role's two-line overlay (`CONFIG_GF_ROLE_UTILITY`,
`CONFIG_GF_STATIC_IP`) layered onto `sdkconfig.defaults` via
`SDKCONFIG_DEFAULTS` above. It is not disposable the way `sdkconfig` or
`sdkconfig.old` are (both gitignored, both regenerated by `set-target`) —
deleting it means nobody can reproduce the utility build from a clean
checkout.

The static IP you set in `menuconfig` is what you type on the hub's `/cal`
page. Give it a reservation on the router too, or pick one outside the DHCP
pool.

## Flash (first time, over USB)

Already shown above per role: `idf.py ... -p COMx flash monitor`. Watch the
monitor for `up at <the static IP>`, then confirm from another machine on
the LAN:

```
curl http://192.168.1.51/api/telemetry
```

## OTA (every time after that)

Two app slots (`partitions.csv`), rollback on
(`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`). From any PC on the LAN, no USB
needed:

```
curl --data-binary @build_sump/gf_node.bin http://192.168.1.51/ota
```

The node streams the image into whichever slot is not currently running,
validates it (`esp_ota_end` checks the image header and checksum — a text
file or the wrong role's `.bin` is refused with `400` before it is ever
booted), and reboots into it. `POST /ota` replies before the reboot:

| Response | Meaning |
| :--- | :--- |
| `200 OK N bytes, rebooting into ota_N` | written, validated, rebooting |
| `400` | body too small, or not a valid ESP32 app image |
| `413` | image larger than the OTA slot |
| `500` | partition, write, or boot-partition-set failure |

None of the failure responses reboot the node or leave the target slot in a
state that blocks a second attempt — a bad push just means try again.

The new image boots **pending-verify**. `main.c`'s watch marks it good only
once the node has Wi-Fi **and** has answered one `/api/telemetry` request;
if that has not happened within 120 s (`OTA_CONFIRM_MS`, `gf.h`) it reboots
into the previous image by itself. So a build with the wrong SSID or
password costs two minutes of monitor log, not a trip to a manhole or a
motor starter panel.

The hub shows each node's `fw` (the git description) in its node list, which
is how you know a push actually landed.

## What it answers

`GET /` — one line of identity. `GET /api/telemetry` — the JSON in the spec
§4, raw readings only; every calibration number lives on the hub.
`POST /ota` — above.
